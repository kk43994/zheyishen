状态：第一、二阶段核心已实现；结构化实体状态机与实战调参待继续  
对应内容规范：`fate-policy-1.0`

2026-07-28 已落地：

- 后台预取支持取消、世代隔离和最多两轮定向尝试。

- 新增 `validate:fate-residue` 回归，覆盖抽象隐喻误加属性、候选外道具、重复道具、极端配方和账号类道具。

## 1. 结论

命运牌拆成两个彼此独立的系统：

1. **AI 叙事层**只决定发生了什么、主角如何回应、这次回应在剧情里留下了什么。
2. **本地规则层**根据剧情证据、当前构筑和本轮预算，决定属性、道具、资源或规则效果。

AI 在战斗开始后后台预生成。命运牌触发时只读取已经就绪的结果，绝不等待网络：

```text
章节开始
→ 同步准备一张本地保底牌
→ 后台生成 AI 牌并做程序校验
→ 校验通过后原子替换“就绪槽”
→ 触发时直接读取就绪槽
→ AI 未完成、失败或过期：同一帧使用本地保底牌
```

因此，网络、模型超时、账号余额和服务故障都只能影响“本次使用 AI 牌还是保底牌”，不能影响战斗、转场、帧率或玩家操作。

## 2. 玩家体验不变量

实现必须同时满足：

- 命运牌出现前不展示加载状态、转圈或“AI 正在生成”。
- 触发命运牌的代码路径中没有 `await`、网络请求或重试。
- 玩家看到的每一项属性、道具和规则变化，都能从刚刚发生的剧情中指出直接依据。
- 允许变化非常极端，但“极端”来自明确的获得、损伤、习惯或交换，不来自随意比喻。
- 一段剧情没有留下可结算的东西时，可以只留下记忆或五毒；不得为了奖励完整而硬塞属性。
- AI 迟到的结果不得替换已经展示或已经选择的命运牌。
- 断网和模型不可用时，玩家仍然能够完整通关。

## 3. 从剧情到机制的因果距离

每个结算先判断“剧情证据离机制有多远”。

| 距离 | 剧情实际发生了什么 | 允许结算 |
|---|---|---|
| A. 直接事实 | 钱被拿走、身体受伤、物品被交到手中、旧物被毁 | 对应的生命、零钱、道具或物品状态 |
| B. 身体或习惯 | 主角反复练习一种呼吸、形成持续动作、身体或穿戴物发生长期改变 | 属性、攻击效果、开局状态或规则变化 |
| C. 象征联想 | 只有一句话、尴尬、目光、颜色或文学隐喻 | 记忆、五毒、回响；原则上不改战斗数值 |

例如：

- “他把钥匙塞进主角手里，主角带着钥匙离开”可以获得对应道具。
- “他在这一年里练会了把一口气分成三段”可以获得散射或三段攻击。
- “拖鞋在心里变重了”不能因此让伤害增加；这只有象征联想，没有身体或装备变化。

一项结算必须通过三道问题：

1. 能否指出 `fact` 或 `result` 中的具体证据句？
2. 玩家在看到数值前，能否大致猜出它会改变哪一类机制？
3. 如果把剧情中的核心物件换成任意别的物件，这套结算是否仍然成立？若仍然成立，通常说明关联过于泛化。

## 4. AI 返回“剧情残留”，不返回最终数值

回应结构新增 `residue`。AI 只能从程序提供的枚举和候选 ID 中选择：

```ts
type FateResidueCarrier =
  | 'item'
  | 'body'
  | 'habit'
  | 'resource'
  | 'worn_item'
  | 'memory'
  | 'none';

type FateResidueMotif =
  | 'guard'
  | 'focus'
  | 'scatter'
  | 'haste'
  | 'weight'
  | 'reach'
  | 'echo'
  | 'store'
  | 'return'
  | 'release'
  | 'debt'
  | 'wound'
  | 'recovery'
  | 'possession'
  | 'loss';

type FateResidueIntensity = 'normal' | 'wild' | 'rule_break';

interface FateResidueIntent {
  carrier: FateResidueCarrier;
  motif: FateResidueMotif;
  intensity: FateResidueIntensity;
  evidence: string;
  candidateItemId?: ItemId;
  recipeId: string;
}
```

字段含义：

- `evidence` 是给玩家和日志看的短句，必须来自 `fact` 或该回应 `result`，不得新写原因。
- `candidateItemId` 只能来自程序给出的合法候选物品。
- `recipeId` 只能来自程序本轮下发的合法机制配方。
- `intensity` 只是请求预算档位，不代表 AI 有权决定最终强度。
- 当前 v2 使用“原文证据 + 封闭枚举 + 配方注册表”作为最小可验证合同；后续 v3 再增加 `entityCatalog/transitionIds`，不影响现有存档。

旧的 `effect/stats` 在迁移完成后不再由 AI 生成。最终结算由程序产生：

```ts
interface FateSettlement {
  version: 2;
  evidence: string;
  carrier: FateResidueCarrier;
  motif: FateResidueMotif;
  intensity: FateResidueIntensity;
  recipeId: string;
  primary: 'item' | 'stats' | 'effect' | 'resource' | 'memory' | 'none';
  candidateItemId?: ItemId;
}
```

一条回应只有一个 `primary` 主结算。五毒和事实/选择记忆可以伴随记录，但不能再额外叠一份主奖励。获得道具时，道具本身的能力就是本次主结算，不再同时赠送另一套无关属性。

`effect/stats/gainItemId/hint` 仍保存在 `FateResponse` 上供运行时和旧存档读取，但对 AI v2 事件而言，它们全部由程序根据 `recipeId` 编译，不从模型输出中取值。

## 5. 本地“剧情结算编译器”

编译器输入：

```ts
interface FateSettlementContext {
  profile: FateProfile;
  responseDirection: 'swallow' | 'exhale';
  residue: FateResidueIntent;
  latestSnapshot: LifeSnapshot;
  entityCatalog: EntityCatalog;
  allowedTemplates: FateSettlementTemplate[];
  seed: number;
}
```

编译顺序：

1. 校验证据确实存在于当前事件文本中。
2. 校验人物、物品和状态转换都属于封闭世界。
3. 根据因果距离决定允许的结算载体。
4. 从本轮 `allowedTemplates` 中筛选与 `carrier + motif` 匹配的模板。
5. 根据命运轮廓、当前构筑、章节和安全上下限确定最终数值。
6. 运行可玩性检查；无合法结果时降级为记忆或五毒，不猜测新机制。
7. 生成玩家可见的机械说明，保存证据和模板 ID 进入回执。

编译器必须是确定性的：同一个快照、种子和 `residue` 必须得到同一个结果。

当前 v2 已实现安全降级：已知普通配方的结构正确、证据也确实来自 `result`，但证据不足以证明身体/习惯/穿戴物/资源变化时，编译为 `memory_only`；未知配方、候选外道具、事实中未出现的分支道具、伪造证据等硬错误仍拒绝整张事件。

### 5.1 机制配方注册表

极端效果不应由通用的百分比随机拼接，而应来自人工实现和压测过的成套配方：

```ts
interface FateMechanicRecipe {
  id: string;
  kind: 'stats' | 'effect';
  requiresCarrierKinds: FateResidueCarrier[];
  requiresAllTags?: string[];
  requiresAnyTags?: string[];
  minPersistence: 'scene' | 'next_battle' | 'chapter' | 'run';
  operations: readonly MechanicOperation[];
  visualSignature: string;
  balanceCost: number;
}
```

例如“镜片裂开并继续佩戴”可以匹配“每发形成一实一虚的错位双影，虚影延迟命中，弹宽大幅收窄”。换成一把普通勺子时这个配方就不成立，因此它比“因为难过，所以伤害 +70%”更强、更好记。

关联强度与数值强度分开判断：

- A 级：锚点、持续、方向、替换、预判和画面测试全部成立；可以改规则或使用极端配方。
- B 级：存在真实载体，但持续或视觉联系较弱；只能使用普通属性或下一战效果。
- C 级：只靠情绪与象征隐喻；只能留下记忆、五毒或 `none`。

### 5.2 道具

获得道具必须同时满足：

- 剧情中存在一个具体对象；
- 对象来自 `fateItemCandidates`；
- `result` 明确写出它从现场或人物手中转移给主角；
- `stateTransitions` 包含 `scene/actor → inventory`；
- 展示时主角仍未拥有该道具。

若物品只被看见、想起、比作或短暂触碰，不得获得道具。实体物要求明确转交；会员、账号记录等非实体物要求明确开通、续费、绑定、保存或记入账号。候选物还必须先逐字出现在 `fact`，程序才会向回应阶段开放对应 `keep_item:` 配方。道具是在某个回应之后获得的，应放在该回应的 `FateSettlement`，不能伪装成选择前已经发生的 `unavoidable.gain_item`。

### 5.3 属性和规则效果

允许三档强度：

| 档位 | 主要变化 | 代价 | 用途 |
|---|---:|---:|---|
| `normal` | 约 10%–25% 或一个轻量效果 | 可无或 5%–15% | 微光、普通交换 |
| `wild` | 一条主轴约 40%–100% | 另一条约 20%–60% 或明确持续代价 | 诱惑、反噬、强交换 |
| `rule_break` | 攻击方式或回合规则改变 | 必须有可理解的限制 | 荒诞、稀有事件 |

数值只是初始设计区间，最终必须经过实战压测。规则：

- 一次只允许一条“离谱主轴”，避免玩家无法理解变化来源。
- 极端收益必须有直接、可见、同源的代价。
- 代价不能是假代价，例如给不依赖弹速的流派降低弹速。
- 射速、移速、弹宽等必须设运行时硬上下限，不能产生零间隔、负数、无限碰撞或出界。
- `rule_break` 优先使用已有白名单效果，不允许模型创造代码中不存在的能力。

### 5.4 六种轮廓的结算职责

| 轮廓 | 结算倾向 |
|---|---|
| 微光 | 小幅修复、保护或一个有条件的出口 |
| 交换 | 一个明确得到与一个同源失去 |
| 诱惑 | 巨大即时收益与长期、可感知的成本 |
| 反噬 | 当前最强构筑轴被现实扭转、放大或反咬 |
| 荒诞 | 改变攻击规则、存储方式或触发顺序 |
| 沉默 | 可以只留下记忆、五毒或延迟标记，不强发奖励 |

轮廓决定预算，不决定文学内容，也不允许覆盖剧情证据。

## 6. 后台生成的运行结构

新增一个独立的 `FateDirector`。它不参与每帧战斗逻辑，只管理三个有限状态：

```ts
interface FateReadySlot {
  encounterIndex: number;
  runSerial: number;
  generationId: number;
  snapshotHash: string;
  dependencies: FateDependencies;
  status: 'warming' | 'ready' | 'failed' | 'consumed';
  event?: FateEventDraft;
  startedAt: number;
  finishedAt?: number;
  failureCode?: string;
}

interface FateDirectorState {
  fallback: FateEvent;
  current?: FateReadySlot;
  next?: FateReadySlot;
}
```

状态流转：

```text
startStage
├─ 同步：按种子选择并校验 fallback
└─ 异步：warming
           ├─ 本地硬校验通过 → ready
           ├─ 超时/失败 → failed
           └─ 新局/章节失效 → 丢弃

fateTrigger
├─ ready 且依赖仍有效 → consume AI event
└─ 其他任何状态 → consume fallback
```

`fateTrigger` 不改变 `warming` 任务的优先级，也不等它结束；它只消费此刻已经存在的内容。

### 6.1 双缓冲

- `current`：本章下一张可能展示的牌。
- `next`：当 `current` 就绪且后续章节已具备稳定上下文时，低优先级预热下一张。
- `fallback`：同步、确定性、本地可用，永远存在。

不能无限提前生成。命运牌依赖的年龄、记忆和穿戴物尚未确定时，不建立 `next`，防止生成大量过期内容和浪费费用。

### 6.2 快照与过期

生成上下文拆成两层：

- **`contentKey` 稳定字段**：Schema/提示词/模型版本、局种子、命运序号、章节、年龄、正典版本、可引用记忆 ID、可引用道具 ID 和预选剧情锚点。
- **`compileState` 易变字段**：生命、零钱、当前穿戴物、候选物品、构筑数值、五毒和临时状态。

AI 可以引用易变字段，但必须在 `dependencies` 中声明。触发时用最新快照检查：

- 只发生数值变化：保留剧情，用最新状态重新编译结算。
- 被引用物品已失去、候选道具已拥有、记忆或人物状态冲突：整张 AI 牌过期。
- 无法证明安全：使用保底，不临场重生成。

不得只对完整 `LifeSnapshot` 做一个总哈希。掉 3 点生命不应使一张与生命无关的剧情作废；真正被引用的眼镜已经遗失，则必须作废。结果至少声明 `usedMemoryIds/usedItemIds/usedCandidateItemIds`，触发时只检查真实依赖。

### 6.3 并发、超时与取消

- 同一局最多一个高优先级命运牌生成任务。
- 新局、重置或章节变化时调用 `AbortController.abort()`；不支持取消的端只用 `runSerial + generationId` 丢弃迟到结果。
- 后台任务设置总截止时间，不把多个 20–30 秒超时串成一分钟以上的流水线。
- 程序硬校验是最终门；同模型自审不是阻断链路中的权威步骤。
- 文学化和命运回响属于可选增强，错过预算时直接使用已通过的底稿或本地文本。
- 连续失败达到阈值后，本局打开熔断器，只使用本地事件；下一局或冷却后再试。
- AI 回调只能发布一个通过校验的候选，不能直接弹窗、扣血、给钱、发道具或写正典记忆；暂停和页面隐藏时尤其如此。

抖音生产端初始并发固定为 1；确认平台和真机行为后才能提高。单次结构化生成软截止建议 8–10 秒；只有距离触发仍有足够窗口时才允许一次定向重试。连续 2–3 次平台错误或超时后熔断约 60 秒。

推荐把现有五段串行模型调用收敛为：

```text
一次结构化草稿生成
→ 本地硬校验
→ 最多一次定向修复
→ 可选文学化（不影响是否已有可展示牌）
```

## 7. 触发代码必须同步

目标代码形态：

```ts
private openFate(destination: FateDestination): void {
  const latest = this.buildLifeSnapshot();
  const selected = this.fateDirector.consume({
    encounterIndex: this.encounterIndex,
    latestSnapshot: latest,
  });

  const event = compileFateEvent(selected.event, latest);
  this.presentFate(event, selected.source);
}
```

其中 `consume()` 和 `compileFateEvent()` 都只能执行有界的本地计算。触发后才暂停战斗并展示纸窗；不能先设置一个很长的 `spawnPause` 再等待 AI。

“有件事正在发生”如果保留，只能是按关卡时间触发的剧情预兆，不能绑定 `requesting/ready` 状态，否则玩家仍能感知模型延迟。

## 8. 亲口回应

亲口回应取决于玩家刚输入的文字，无法提前生成。仍采用非阻塞设计：

1. 玩家提交时立刻保存“他说出了这句话”。
2. 本地规则根据当前命运牌预算执行一个安全、可解释的即时结算，或只记录五毒与记忆。
3. 关闭纸窗并继续战斗。
4. AI 在后台生成现场人物的一次直接反应，校验通过后作为页边回响出现。
5. 超时、失败或违规时不显示回响，不回滚已经提交的回应。

这样玩家的自由表达仍被承认，但模型永远不能卡住游戏，也不能迟到后修改数值。

## 9. 存档与日志

存档只保存：

- 已通过校验的 `ready` 牌及其依赖清单；
- 已消费的命运回执；
- 规则、提示词、Schema 和模型版本。

不保存 Promise 或半成品请求。读档时重新校验 `ready` 牌；不合格就丢弃并使用保底或重新预热。

每个后台任务记录：

```text
traceId / runSerial / generationId / encounterIndex
snapshotHash / dependencyIds
startedAt / finishedAt / stageLatency
accepted / stale / aborted / fallbackReason
model / promptVersion / policyVersion
tokens / estimatedCost
```

日志不得包含 API Key 或未经脱敏的玩家输入。

## 10. 对当前代码的最小改造

第一阶段只解决“绝不等待”：

1. 把 `game.ts` 的 `prefetchedFate.promise` 改为 `warming/ready/failed` 槽。
2. `prepareFate()` 在后台填槽，同时同步准备本地保底。
3. `openFate()` 删除异步闭包和 `await`；只取 `ready` 或 `fallback`。
4. 删除为了等 AI 而设置的 `spawnPause = 999`；仅在真正展示命运牌时暂停。
5. 新局、读档和章节切换时同时推进 `runSerial/generationEpoch`，取消或废弃旧任务。
6. 把已就绪牌和依赖清单纳入断点存档。
7. 修复命运道具的存档校验：历史回执按“当时的结算快照”读取，不能再用玩家已经拥有该物品这一结果反过来判定原事件非法。
8. 选择提交后先写入不可变回执再播放结果动画，避免退出后重新选择。

第二阶段核心已经解决“剧情和机制真关联”：

1. `fate.ts` 已增加 `FateSettlement` 与剧情残留合同。
2. 已建立原文证据、载体、轮廓强度、候选道具与归属变化校验。
3. 已增加确定性的本地配方注册表和编译器。
4. 分支获得道具已经进入回应结算，并要求事实页先放入现场。
5. AI v2 输出的 `hint/effect/stats` 不再被接受，最终数值只来自程序配方。

完整 `entityCatalog/transitionIds` 状态图作为后续加固，不再阻塞当前 v2 使用。

第三阶段提高质量和成本效率：

1. 合并不必要的模型阶段，去掉关键路径上的同模型自审。
2. 增加定向修复、熔断、去重和生成结果落盘。
3. 用实战数据调整 `normal/wild/rule_break` 预算。
4. 建立命运牌首次通过率、AI 就绪率、降级率、延迟和成本看板。

## 11. 验收标准

交互性能：

- 断网、余额不足、模型 60 秒无响应时，命运牌仍在触发帧内打开。
- `openFate()` 及调用链不包含网络等待。
- AI 迟到后不会替换已展示牌。
- 新局不会收到上一局结果。
- 后台生成期间战斗帧时无可感知卡顿。

剧情结算：

- 每个属性、道具和规则变化都保存 `sourceEvidence`。
- 候选外道具获得率为 0。
- 只有象征联想的样本产生战斗属性变化的比例为 0。
- 同一输入、快照和种子得到相同结算。
- 固定极端样本不会造成负射速、零攻击间隔、无限弹体或不可恢复的软锁。

体验质量：

- 玩家在不看开发日志时，也能说清“为什么这个回应带来了这个变化”。
- `wild` 选择确实能改变构筑方向，而不是多个小数值相加。
- “没有物质回报”可以成为有意义的结果，不被系统自动补偿。
