# 命运牌 AI 测试与实现审计

日期：2026-07-28  
测试模型：`doubao-seed-2-1-turbo-260628`  
对应规范：`fate-policy-1.0`

本文是一次性评测与实现审计，不是内容正典。

## 1. 模型实测

### 1.1 出生档案

| 样本 | 结果 | 延迟 |
|---|---|---:|
| 大富、部队大院、青春伤感、`harsh` | JSON、家庭、地域、特质方向和外貌白名单均合格 | 直连约 16.3 秒 |
| 贫困、海边、灰色幽默、`favored` | JSON 合格，贫困与幸运正确解耦 | 代理约 15.7 秒 |
| 同类完整请求 | 一次代理超时 | 42 秒 |

### 1.2 现实审稿

| 样本 | 期望 | 实际 | 延迟 |
|---|---|---|---:|
| 信封自己说话；中年回到初二早自习 | 拒绝 | `valid=false`，指出两处硬伤 | 约 5.4 秒 |
| 人物、时间、地点和因果连续的公司会议 | 通过 | `valid=true` | 重试后约 7.0 秒 |
| 上游请求 | 成功 | 出现一次 `fetch failed`，重试恢复 | — |

### 1.3 回应生成与自审漏检

输入事实只出现医院、收费员、收据和已经完成的医保扣费。模型生成的回应额外加入：

- 公文包；
- 去公司处理积压工作；
- 台阶水渍；
- 下一号病人及其咳嗽；
- 输入未明确给出的医保明细展示动作。

这些内容违反回应的封闭世界。把同一结果交给 `fate-review` 后，模型仍返回：

```json
{
  "valid": true,
  "reason": "通过"
}
```

结论：

- 中文叙事与 JSON 格式：良好；
- 一般规则理解：良好；
- 多重硬约束持续遵守：不稳定；
- 同模型自审：不能作为硬校验；
- 热状态短审稿约 4–7 秒，完整生成约 15–16 秒；
- 观察到超时和网络失败，必须重试并保留本地保底。

## 2. 当前运行链路

当前 `generateAIFate` 实际执行：

```text
fate 事实核心
→ 本地格式与写实正则
→ fate-options 两个回应
→ 本地结构、年龄与剧情残留校验
→ fate-review 语义审稿
→ 放入后台就绪槽；失败最多循环两轮后保留本地事件
```

玩家提交后：

```text
程序执行不可避免效果与回应效果
→ 保存 FateReceipt
→ fate-result 异步生成命运回响
```

亲口回应不再走独立 `fate-free` 模型路由：玩家先明确选择“咽下/吐出”，程序同步执行该方向已经校验的本地结算，AI 仅异步补写 `fate-result` 回响。

## 3. 已确认的实现差距

| 优先级 | 差距 | 证据与影响 |
|---|---|---|
| P0 | 封闭世界不是硬校验 | 当前主要依赖提示词和 `fate-review`；实测同模型漏检 |
| P1 | 文本阈值不一致 | 提示词要求 `fact` 40–120、普通 `result` 12–90；底层验证器分别允许低至 8 和 6 字 |
| P1 | 预取快照可能陈旧 | 命运牌在章节开始预生成，章末优先复用；期间生命、零钱、物品与记忆可能已经变化 |
| P2 | 生成字段与可见字段未区分 | 当前 UI 不直接展示 `scene` 或模型返回的 `hint`，机械提示由程序从效果生成 |
| P2 | 出现次数属于运行配置 | 当前正常流程实际在少年、成年、中年、晚年出现 4 次；内容规范不应把次数写死 |
| P2 | 生产审计仍是设备本地 | 已记录模型、延迟、状态与关键游戏节点，但尚无跨设备聚合、tokens 与费用看板 |

## 4. 修复顺序

1. 增加结构化实体、位置、可用状态与状态转换合同。
2. 在展示预取结果前，用最新快照再次校验所有相关状态。
3. 统一文本阈值，让非法字段整项拒绝而不是静默裁剪。
4. 建立固定正反例、逐卡 trace、tokens/费用记录与模型评测报告。

## 5. `fate-policy-1.0` 定向回归

本轮在规范重写后直接调用当前运行端点。规范尚未接入提示词或校验器，因此测试目标是衡量当前实现与新规范的距离。

| 用例 | 端点 | 结果 | 延迟 |
|---|---|---|---:|
| 童年事实：明确输入“尚未上学” | `fate` | 通过；事件发生在家中卧室，没有进入学校 | 6.129 秒 |
| 中年事实：加班、裁员记忆、裂纹眼镜 | `fate` | 通过；年龄、办公室场景和当前穿戴物连续 | 5.119 秒 |
| 医院已扣费后的两个回应 | `fate-options` | 失败；新增随身包、上班任务、积压工作和排队 NPC | 6.881 秒 |
| 对上述违规回应自审 | `fate-review` | 失败；错误返回 `valid=true` | 2.340 秒 |
| 亲口回应“其实我是奥特曼” | `fate-free` | 部分理解正确：没有真的变身；但新增老人、保安和橡胶棍，违反封闭世界 | 6.303 秒 |

五次请求均返回 HTTP 200。这个小样本的延迟中位数约 6.1 秒，最慢约 6.9 秒；样本量不足以当作正式 P95。

### 5.1 关键失败样本

医院事实只提供：主角、收费员、收据、缴费窗口、已经完成的医保扣费。模型仍生成：

> 把收据塞进随身包，赶去公司处理积活。

以及：

> 后面排队的人小声啧了一声。

这说明模型能避免“重复付款”这种明确模式，但会为自然感主动补充输入中不存在的日常细节。

亲口回应能够把“奥特曼”处理为现实中的一句话，没有生成超能力；但结果又加入：

> 周围排队的老头老太、保安、橡胶棍。

因此 `fate-free` 的“现实化理解”合格，“事实边界控制”不合格。

### 5.2 本轮结论

- 事实核心能力：合格，年龄与局内物品理解较好。
- JSON 与枚举稳定性：本轮合格。
- 回应创作能力：语言自然，但封闭世界不合格。
- 亲口回应理解：能处理玩梗，但会新增未授权角色和道具。
- 自我审稿：出现明确假阴性，不能作为最终质量门。

当前模型可以继续承担创作，但不能在缺少结构化实体与状态校验时直接决定最终入场文本。下一步应先实现规范中的 P0 程序校验，再进行同一组回归；仅继续扩写提示词无法解决本轮暴露的问题。

## 6. 后台生成与触发链路补充审计

当前代码有“章节开始预取”的雏形，但不满足“AI 永远不进入交互关键路径”：

| 优先级 | 问题 | 当前证据 | 影响 |
|---|---|---|---|
| P0 | 触发仍等待 Promise | `game.ts` 的 `openFate()` 等待预取 Promise 或临场 `generateAIFate()`，AI 回调才调用 `presentPendingFate()` | 模型完成时刻决定命运牌出现时刻 |
| P0 | 章末可能重复生成并互相作废 | 转场固定 4.2 秒；结束后再次 `stageEndReward() → openFate()`，但 `openFate()` 期间仍停留在 `battle`，`beginStageTransition()` 没有命运牌请求中的阻断标记 | 慢请求/离线时每 4.2 秒递增 `fateGenerationId`，上一请求即使成功也被丢弃，命运牌可能一直不出现且底层请求不断堆积 |
| P0 | 上一局的请求可能进入新一局 | `startRun()` 清空暂存值但没有推进 `fateGenerationId`；旧回调只比较该 ID，随后可以重新写入 `pendingFateOpen` | 终章请求未完成时死亡并重开，旧命运牌可能在新局第一场战斗弹出 |
| P0 | 获得命运道具后断点可能被判非法 | 展示事实时先取得道具，存档同时保存已拥有道具与原事件；读档又用当前物品列表验证“待获得的道具必须未拥有” | 当前事件和历史回执都可能使后续断点恢复失败 |
| P0 | 章末用超长暂停等 AI | `openFate('advance')` 设置 `spawnPause = 999` | 游戏节奏被 AI 状态控制 |
| P1 | 预取只有 Promise，没有可消费就绪槽 | `prefetchedFate` 仅保存 `encounterIndex + promise`，没有 `ready/failed/consumed`、截止时间和依赖清单 | 无法做到触发时同步选择 AI 牌或保底牌 |
| P1 | 最坏请求链过长 | 一轮依次执行事实、选项、自审、文学化、再审；整轮最多重试四次 | 最坏约 20 次串行模型调用，不适合移动端预取窗口 |
| P1 | 迟到结果只逻辑忽略，没有传输取消和并发控制 | `generationId/runSerial` 能防止部分旧结果落账，但平台调用本身继续占用资源 | 快速重开或重复触发时可能形成隐藏并发和额外费用 |
| P1 | AI 回响进入后续正典记忆 | `generateAIFateResult()` 回调把异步生成文本追加进 `memories` | 可选润色会改变后续生成上下文；迟到时序影响本局正典 |
| P1 | 亲口回应无法预取，且机械字段由 AI 决定 | `fate-free` 返回方向、效果、五毒和属性，玩家提交后等待 | 自由回应必然阻塞，AI 仍能直接修改机制 |
| P1 | 暂停期间回调仍可切屏并执行事实 | 页面隐藏后 `update()` 停止，但 AI 回调只要看到状态仍为 `battle` 就直接展示，并执行扣血、扣钱或发道具 | 玩家未在操作、存档也未同步时，后台回调改变运行状态 |
| P1 | 选择已经结算，结果动画期间却不能存档 | 属性、五毒和回执先执行；`captureCheckpoint()` 在命运结果阶段返回空 | 退出后可能回到未选择状态并重新选择 |
| P1 | 战斗恢复重置时间且不重新预取 | 恢复先写入 `battleTime`，随后 `startStage(true)` 又清零；`resume=true` 同时跳过 `prepareFate()` | 读档后重打一章，并在章末更容易进入重复触发竞态 |
| P1 | AI 回响不保证落盘 | 回响只追加 `memories`，存档去重 key 不含该字段 | 没有其他状态变化时回响不会触发写盘，完成顺序也可能打乱事件顺序 |
| P2 | 本地牌读档后被标成 GPT 来源 | `validateFateEvent()` 固定返回 `source: 'gpt'` | 本地保底恢复后也会额外发起 AI 回响请求 |
| P2 | 就绪牌未随断点存档 | 存档保存回执，不保存已通过的预取结果及依赖 | 读档后预取窗口丢失，更容易走慢请求和重复触发路径 |

正确目标不是“尽量让 AI 快一点”，而是：

```text
章节开始：同步放入一张已校验本地牌
→ AI 后台生成候选
→ 程序校验通过后原子替换就绪槽
→ 命运触发：同步读取就绪槽；没有 AI 牌就立即使用本地牌
```

触发路径必须没有 `await`、重试或网络调用。AI 迟到只能记为 `late_discard`，不能补弹牌、替换牌或追改属性。详细改造合同见《命运牌剧情结算与后台生成设计 v1》。

## 7. 第一阶段修复结果

2026-07-28 已完成：

- `prefetchedFate.promise` 改为 `warming/ready/failed` 预取槽，并始终携带确定性本地保底。
- `openFate()` 改为同步读取；没有就绪 AI 牌时同一调用栈展示保底牌。
- 移除命运触发时的模型请求、等待和 `spawnPause = 999`。
- 新局、读档、章节替换和触发消费会废弃旧世代；可取消的 HTTP 请求使用 `AbortController`。
- 生成链从最多四轮、五段串行收敛为最多两轮“事实 → 回应 → 审稿”，文学化不再阻塞就绪。
- 亲口回应由玩家明确选择咽下或吐出，使用该方向已校验的本地机械结算；AI 只异步生成展示回响。
- 已就绪牌、选择结果和回响展示槽可以写入断点；读档保留来源，并允许验证已经结算的命运道具。
- 新增 `npm run validate:fate-background`，阻断触发路径重新出现 `await`、AI 请求或等待式刷怪暂停。

第二阶段已继续完成：

- AI 回应改为 `residue + recipeId + evidence`，机械 `effect/stats/gainItemId` 只由本地白名单配方编译。
- 分支获得道具、普通/离谱/破规配方已接入，事实中未出现的候选不会开放获得配方。
- `validateFateAge` 已接入完整事件硬校验；童年/少年提示词与本地保底样本已统一。
- 废弃 `fate-style` 与 `fate-free` 的运行路由和提示词已移除，避免文档、代理和实际链路漂移。
- 后台预取、取消、迟到丢弃、断点保存与命运回执均已有自动门禁。

仍待后续阶段处理：结构化实体/位置 diff、展示前最新快照复核、跨设备成本与质量聚合看板。
